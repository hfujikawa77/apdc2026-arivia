What is Arivia?

2 / 13 · What is Arivia? · 目安 0:40 · 累計 1:10 / 8:05

Arivia is an autonomous water-surface drone, made by Space One in Japan.
It was an Honoree of the CES Innovation Awards 2026.
I joined the project to work on the ArduPilot side.
(動画を再生) (While this plays) It has LEDs on the floater and the half-dome.
There is a fountain on top, and a pump underneath draws the water up.
Several units perform a synchronized show on the water.
Under the hood, it's ArduPilot Rover on a Cube Orange, with an X-frame thruster layout.

会社・CES → 自分は ArduPilot 側の開発担当として参加した。動画は音なしなので、流しながら構造(LED / 噴水 / ポンプ)・複数台の同期・構成(Rover / Cube Orange / X フレーム)を話す。仕様は公開情報の範囲で。リンク: https://spacexone.com/ · CES 公式ページ。

GCS ⇄ (Wi-Fi / MAVLink) ⇄ Unit ⇄ FC

3 / 13 · System architecture · 目安 1:05 · 累計 2:15 / 8:05

Here is how the pieces fit.
The GCS is a Raspberry Pi 4, and it runs the show.
Each boat has another Raspberry Pi 4 as its companion computer.
The flight controller is a Cube Orange running Rover.
The key idea is the split.
The flight controller only moves the boat.
Everything else is handled by the companion: the LEDs, the fountain and the web UI.
One JSON timeline, with timecodes, drives position, light and water together.
The GCS and the units talk over Wi-Fi with MAVLink.

One more thing about the web UI.
The flight controller is inside a waterproof case, and the case is hard to open.
So we gave the web UI two features.
One: updating our custom firmware.
Two: setting GUID_OPTIONS, which turns lateral move on.
Now we do both over Wi-Fi, without opening the case.

左から GCS(ショー実行)→ Unit(各機の Raspberry Pi 4 = コンパニオン)→ FC(Cube Orange + Rover)。役割分担(split)が肝: FC は「動かす」だけ。LED・噴水・Web UI は Unit 側。ショー = タイムコード付き JSON。通信は Wi-Fi + MAVLink。 Web UI のエピソード: 防水ケースをなかなか開けられないので、Unit の Web UI に機能を付けた。主目的は 2 つ: ①カスタムファームの更新、②横移動を有効にする GUID_OPTIONS(bit 7)の設定(パラメータの参照・更新)。Wi-Fi 越しにできるので、ケースを開けずに済む。

Why lateral move?

  • X-frame can translate in any direction
  • Rover navigates by "turn, then drive"
  • Shows need the heading held
  • Goal: fixed heading + lateral velocity

4 / 13 · Why lateral move? · 目安 0:30 · 累計 2:45 / 8:05

So, why do we need lateral move?
An X-frame can move in any direction.
But Rover normally turns first, then moves forward.
In a show, that looks wrong.
We want to hold the heading, so the LEDs and the fountain keep facing the audience, while the boat moves sideways.
That means a fixed heading, and a lateral velocity.

役割: なぜ必要か。問題(旋回 → 前進)→ 欲しい動き(機首固定で横移動)→ キーワード fixed heading / lateral velocity。Issue と既存機能の話は 5 枚目に回した(重複させない)。

Use: Auto = CONDITION_YAW · Guided = GUID_OPTIONS bit 7 · omni frames only

6 / 13 · Implementation · 目安 0:50 · 累計 3:55 / 8:05

Here is how we implemented it.
I'm an app developer, not a C++ or control expert.
So I had support from AI, and we checked the changes on the real boat.
The flow has four steps.
First, we receive a position target in Guided or Auto mode.
Second, the waypoint navigation holds the fixed heading.
Third, the position controller splits the velocity into forward and lateral.
Finally, a new lateral PID controls the lateral speed.

How to use it: in Auto, a CONDITION_YAW command sets the fixed heading.
In Guided, set bit 7 of GUID_OPTIONS.
Both work on omni frames only.

5 ページの「Rover 4.6.3 で実装」を受けて、ここでは「実装の中身」に入る(バージョンは繰り返さない)。アプリ開発者で C++・制御は専門外なので、AI のサポートを受けて開発し、実機で確認した。流れ 4 段階(位置目標 → WP nav が固定ヘディング保持 → 位置制御が前後/横に分解 → 新しい lateral PID)→ 使い方(Auto は CONDITION_YAW(MAV_CMD_CONDITION_YAW。コード内の関数名は do_set_yaw。DO_SET_YAW という MAVLink コマンドはない)、Guided は GUID_OPTIONS bit 7、Omni のみ)。落とし穴は次のスライドで話す。

Pitfalls

  • AR_PosControl::init reset the fixed heading
    → lateral output stalled
  • Pivot turn fought the fixed heading
    → Rover turned, we wanted to hold

7 / 13 · Pitfalls · 目安 0:25 · 累計 4:20 / 8:05

We hit two pitfalls along the way.
First, the position controller's init reset the fixed heading, so the lateral output stalled.
Second, the pivot turn fought the fixed heading.
Rover tried to turn the boat, but we wanted to hold the heading.

役割: つまずきの共有(開発者向けの学び)。①AR_PosControl::init が固定ヘディングをリセット → 横の出力が止まった。②pivot turn(その場旋回)が固定ヘディングと競合(Rover は向きを変えようとし、こちらは保持したい)。「fought」が出にくければ "worked against" でもよい。3 つ目の「FF なし」は次の次(11 枚目)で話す。

9 / 13 · It is slow · 目安 0:40 · 累計 5:35 / 8:05

The flight logs confirm what we saw.
We analyzed 19 Guided GoTo moves, with QZSS CLAS positioning and no base station.
On pure lateral moves, the peak speed was 0.23 to 0.31 meters per second.
On forward moves, it was 0.36 to 0.57.
So sideways reached about half the peak speed of forward moves.
But both were far below the 2.0 meters-per-second target.

役割: 速度を計測で裏付ける。EKF 速度を機体座標系に変換した最大速度: 横 0.23〜0.31(5 回)、前進主体 0.36〜0.57(10 回)、目標 2.0 m/s。標本が少ないので目安として話す。「約半分」はここで初めて言う。比較は 2 つ(横 vs 前進のピーク速度 / ピーク速度 vs 目標 2.0 m/s)を、文を分けて言う。平均でなくピーク速度。

It also stops short

  • "Reached" fires 0.3–1.8 m before the target
  • Reason: WP_RADIUS = 2 m
  • Then lateral drive is cut and the boat switches to loiter

10 / 13 · It also stops short · 目安 0:30 · 累計 6:05 / 8:05

It also stops short.
The logs show that "reached" fires 0.3 to 1.8 meters before the target.
Why?
The reason is WP_RADIUS.
It was set to two meters.
Once the boat is inside that circle, Rover says "reached".
Then it cuts the lateral drive, clears the fixed heading, and switches to loiter.
This one we confirmed in the code and the logs.

役割: 手前停止を計測 → 原因(確定)。「到達」が目標の 0.3〜1.8 m 手前で成立(WP_RADIUS = 2 m)→ 横出力を切り、固定ヘディングを消し、Loiter へ。コードとログで確認済み(仮説ではない)。

Logs: fixed heading is set correctly, but no PIDL log and ATT.DesYaw = 0 → tracking can't be seen

11 / 13 · Why slow? · 目安 0:35 · 累計 6:40 / 8:05

So, why is it slow?
We don't know yet.
We can't prove it, because the lateral PID is not logged.
But we have one hypothesis.
In the code, forward has a cruise-throttle feed-forward.
Lateral does not.
Without it, the lateral controller may not push hard enough against drag.
This is not verified.
Next, we'll add lateral PID logging, retest with a smaller WP_RADIUS, and tune the controller.

役割: 原因分析(ここだけ仮説)。「分からない → でも仮説がある」の順。仮説は 1 つに絞る。事実(コードで確認済み): 横方向には cruise throttle の FF がない(lateral_base = 0、前後にはある)。仮説(未検証): それが遅さの原因で、抗力を補い切れていない(may で言う)。未検証と明言。ログ不足(lateral PID が未ログ)が理由。次の一手: PIDL ログ追加、WP_RADIUS を小さくして再試験、ATC_LAT_FF とゲインを 1 つずつ調整。スライドにも「Next: lateral PID log · retest with a smaller WP_RADIUS · tune」を出している(台本の最後の文と対応)。スライドのログ行(ATT.DesYaw = 0)は台本では話さない。他の仮説は想定質問へ。
