4 / 14 · System architecture · 目安 0:55 · 累計 2:20 / 8:55

Here is how the pieces fit.
The GCS is a Raspberry Pi 4, and it runs the show.
Each boat has another Raspberry Pi 4 as its companion computer.
The flight controller is a Cube Orange running Rover.
The key idea is the split.
The flight controller only moves the boat.
Everything else is handled by the companion: the LEDs, the fountain and the web UI.
One JSON timeline, with timecodes, drives position, light and water together.
The GCS and the units talk over Wi-Fi with MAVLink.

The flight controller is in a waterproof case that is hard to open.
So the web UI lets us update the custom firmware and set GUID_OPTIONS over Wi-Fi.

左から GCS(ショー実行)→ Unit(各機の Raspberry Pi 4 = コンパニオン)→ FC(Cube Orange + Rover)。役割分担(split)が肝: FC は「動かす」だけ。LED・噴水・Web UI は Unit 側。ショー = タイムコード付き JSON。通信は Wi-Fi + MAVLink。 Web UI のエピソード: 防水ケースをなかなか開けられないので、Unit の Web UI に機能を付けた。主目的は 2 つ: ①カスタムファームの更新、②横移動を有効にする GUID_OPTIONS(bit 7)の設定(パラメータの参照・更新)。Wi-Fi 越しにできるので、ケースを開けずに済む。

Why lateral move?

  • X-frame can translate in any direction
  • Rover navigates by "turn, then drive"
  • Shows need the heading held
  • Goal: fixed heading + lateral velocity

5 / 14 · Why lateral move? · 目安 0:30 · 累計 2:50 / 8:55

So, why do we need lateral move?
An X-frame can move in any direction.
But Rover normally turns first, then moves forward.
In a show, that looks wrong.
We want to hold the heading, so the LEDs and the fountain keep facing the audience, while the boat moves sideways.
That means a fixed heading, and a lateral velocity.

役割: なぜ必要か。問題(旋回 → 前進)→ 欲しい動き(機首固定で横移動)→ キーワード fixed heading / lateral velocity。Issue と既存機能の話は 6 枚目に回した(重複させない)。

7 / 14 · Implementation · 目安 0:55 · 累計 4:05 / 8:55

Here is how we implemented it.
I'm an app developer, not a C++ or control expert.
So I had support from AI.
We tested the changes in simulation first, and then on the real boat.
First, the existing flow.
Rover aims at the target, turns, and then drives.
For lateral move, we changed four places.

First, the mode sets a fixed heading.
In Auto, a CONDITION_YAW command sets it.
In Guided, set bit 7 of GUID_OPTIONS.
Both work on omni frames only.
Second, the waypoint navigation holds that heading.
Third, the position controller splits the velocity into forward and lateral.
Fourth, a new lateral PID controls the lateral speed.

役割: 既存の処理と、どこを変えたか(クラス単位の対比)。6 ページの「Rover 4.6.3 で実装」を受けて、ここでは中身に入る(バージョンは繰り返さない)。アプリ開発者で C++・制御は専門外なので、AI のサポートを受けて開発し、先に SITL(シミュレーション)で、そのあと実機で確認した(8 ページの落とし穴は SITL で見つけたもの)。既存: 目標へ向きを回して(turn)、前進(drive)。変更 4 か所(スライドで印): ①モードが固定ヘディングを設定(入口: Auto は CONDITION_YAW(MAV_CMD_CONDITION_YAW。コード内の関数名は do_set_yaw。DO_SET_YAW という MAVLink コマンドはない)、Guided は GUID_OPTIONS bit 7 を立てたとき。Omni のみ)→ ②AR_WPNav が固定ヘディングを保持 → ③AR_PosControl が速度を前後/横に分解 → ④AR_AttitudeControl に新しい lateral PID。入口のあとの処理は Auto と Guided で共通(Mode::navigate_to_waypoint() の「omni かつ固定ヘディング中」の分岐)。落とし穴は次のスライドで話す。

8 / 14 · Pitfalls · 目安 0:55 · 累計 5:00 / 8:55

We hit two pitfalls in the simulator.
We sent five targets with the heading fixed at 290 degrees.
The first one worked.
The second one never arrived.
The boat only wiggled in place.

Pitfall one: the pivot turn.
The second target was 122 degrees off the heading.
That is over the 60 degree pivot angle, so the waypoint navigation started a pivot.
The pivot tried to turn the boat, but we wanted to hold the heading.
Nothing moved.
Now the pivot is disabled while the heading is fixed.

Pitfall two: the init.
The position controller's init clears the fixed heading, so the lateral speed was zero.
Now we re-apply the heading after init.

役割: つまずきの共有(開発者向けの学び)。SITL で見つけたもの(実機の水上ではない)。条件: 固定方位 290° で 5 地点を順に送る。1 つ目(方位角 ≈283°、差 7°)は到達、2 つ目(方位角 ≈52°、差 122°)はその場で左右にゆっくり動くだけで到達しない。 ① pivot turn(主因) — 起きた箇所: AR_WPNav(pivot の判定)。原因: 方位差 122° が WP_PIVOT_ANGLE(既定 60°)を超えて pivot が起動し、横速度が 0 に強制される。pivot は目標へ、モードは 290° 保持で、互いに打ち消し合う。対応: 固定ヘディング中は pivot を無効化(set_fixed_heading() と、update() の毎周期)。 ② init リセット — 起きた箇所: AR_WPNav ↔ AR_PosControl の状態の受け渡し。原因: AR_PosControl::init() が固定ヘディングのフラグを false に戻すので、通常の航法(向きを目標へ旋回)になり、横速度が 0。対応: init_pos_control_if_necessary() で、init のあとに固定ヘディングを再適用。設計上は、状態を 2 か所が持つ構造の弱点(質疑で聞きたいところ)。3 つ目の「FF なし」は 12 枚目で話す。

11 / 14 · It also stops short · 目安 0:40 · 累計 6:55 / 8:55

It also stops short.
"Reached" fires when the boat is inside WP_RADIUS.
It was set to two meters.
So the boat can be declared "arrived" up to two meters early, in any direction.
Then Rover cuts the lateral drive, clears the fixed heading, and switches to loiter.
In the logs, sideways moves ended about 0.6 meters short.
Forward moves ended about 0.3 meters short.
Why is sideways worse?
Probably because it is slower.
We have not verified that yet.

役割: 手前停止を計測 → 仕組み(確定)+ 横のほうが大きい理由(仮説)。確定(コード): 「到達」は WP_RADIUS(= 2 m)の内側に入った時点で成立するので、方向に関係なく最大 2 m 手前で成立しうる。その後、横出力を切り、固定ヘディングを消し、Loiter へ。計測(2026-04-19、Guided GoTo 19 回、粗い見積もり: 「指定距離 − 最大移動距離」): 手前で止まった量の中央値は、横 約 0.6 m(5 回)、前進 約 0.3 m(10 回)。前後も手前で止まっており(前後には目標を越える回も 3 回)、「前後は到達、横は未到達」ではなく程度の差。仮説(未検証): 横のほうが遅い(ピーク 約 0.3 vs 約 0.55 m/s)ので、目標位置の動き(約 5 秒で終わる)に遅れ、2 m の境界の近くで「到達」になる。以前の「0.3〜1.8 m 手前」は、再解析で再現できなかったので使わない。

12 / 14 · Why slow? · 目安 0:35 · 累計 7:30 / 8:55

So, why is it slow?
We don't know yet.
We can't prove it, because the lateral PID is not logged.
But we have one hypothesis.
In the code, forward has a cruise-throttle feed-forward.
Lateral does not.
Without it, the lateral controller may not push hard enough against drag.
This is not verified.
Next, we'll add lateral PID logging, retest forward and sideways moves with a smaller WP_RADIUS, and tune the controller.

役割: 原因分析(ここだけ仮説)。「分からない → でも仮説がある」の順。仮説は 1 つに絞る。事実(コードで確認済み): 横方向には cruise throttle の FF がない(lateral_base = 0、前後にはある)。仮説(未検証): それが遅さの原因で、抗力を補い切れていない(may で言う)。未検証と明言。ログ不足(lateral PID が未ログ)が理由。次の一手: PIDL ログ追加、WP_RADIUS を小さくして前後・横の両方で再試験、ATC_LAT_FF とゲインを 1 つずつ調整。スライドにも「Next: lateral PID log · retest fwd / lateral with a smaller WP_RADIUS · tune」を出している(台本の最後の文と対応)。スライドのログ行(ATT.DesYaw = 0)は台本では話さない。他の仮説は想定質問へ。
